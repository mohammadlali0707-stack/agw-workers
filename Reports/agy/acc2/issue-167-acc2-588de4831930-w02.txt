### 1. Root Cause & Defect Mechanism Analysis

In [.github/workflows/gate-webhook-health.yml](file:///home/runner/work/_temp/agent-repo-43355256834-1-run-agy/.github/workflows/gate-webhook-health.yml#L136-L141), endpoint reachability is probed via:
```bash
STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
  -X POST "$EXPECTED_URL" \
  -H "Content-Type: application/json" \
  -d '{"action":"health_check","test":true}' \
  --max-time 10 2>/dev/null || echo "000")
```

#### Defect Chain Breakdown:
1. **Double '000' Stdout Concatenation (`000000` / `000\n000`):**
   - When `curl` encounters a timeout (`--max-time 10`, exit code 28 `CURLE_OPERATION_TIMEDOUT`), connection refusal (exit code 7 `CURLE_COULDNT_CONNECT`), or DNS failure (exit code 6), libcurl formats `%{http_code}` as `000` to standard output before terminating with a non-zero exit code.
   - Because `curl` exited non-zero, the shell's short-circuit `||` executes `echo "000"`, outputting a second `000\n`.
   - Command substitution `$()` captures all stdout emitted within the subshell, combining both outputs into `"000000\n"`. Stripping trailing newlines yields:
     $$\text{STATUS} = \text{"000000"}$$
   - If curl outputs newlines or runs unbuffered, this produces multiline `000\n000`.
2. **Curl Exit Code Masking:**
   - Because `echo "000"` exits with 0, `$?` is reset to 0 upon completion of `$()`. Curl's true exit code (28, 7, 6, 35) is discarded, leaving no indicator of network failure type.
3. **Arithmetic and Equality Parsing Breakdown:**
   - Line 154 evaluates:
     ```bash
     elif [ "$STATUS" = "000" ] || [ "$STATUS" -ge 500 ] 2>/dev/null; then
     ```
     - `[ "000000" = "000" ]`: Evaluates to **FALSE** (6 characters vs. 3 characters).
     - `[ "000000" -ge 500 ]`: Bash parses `"000000"` as integer `0`; `0 -ge 500` evaluates to **FALSE**.
     - For multiline `"000\n000"`, the test throws `integer expression expected` (exit code 2), silenced by `2>/dev/null`, evaluating to **FALSE**.
4. **Telemetry Inversion Fallthrough (`FAIL_TYPE=config_error`):**
   - Because neither `200/400`, `404`, nor line 154 matches, execution drops into the catch-all `else` block (line 160):
     ```bash
     FAIL_TYPE=config_error
     FAIL_MESSAGE="HTTP 000000: Unexpected HTTP response received from webhook endpoint."
     ```
5. **Downstream Alert Misdirection (Gate 2 Step 4):**
   - In Step 4 (`Post alert if webhook health fails`), `FAIL_TYPE=config_error` triggers the alert category `⚠️ Configuration Error (HTTP 404 / Webhook Config)`.
   - On-call engineers receive alerts advising them to verify GitHub repository webhook settings or trigger workflow reactivation scripts, obscuring the true problem: **the server host is down, unreachable, or timing out**.

### 3. Recommended Remediation & Test Assertions

1. **Idiomatic Two-Stage Capture Pattern:**
   ```bash
   HTTP_CODE=""
   CURL_EXIT=0
   HTTP_CODE=$(curl -s -S -o /dev/null -w "%{http_code}" \
     -X POST "$EXPECTED_URL" \
     -H "Content-Type: application/json" \
     -d '{"action":"health_check","test":true}' \
     --max-time 10 2>/dev/null) || CURL_EXIT=$?

   if [ $CURL_EXIT -ne 0 ] || [ -z "$HTTP_CODE" ]; then
     STATUS="000"
   else
     STATUS="$HTTP_CODE"
   fi

   echo "HTTP_STATUS=$STATUS" >> "$GITHUB_ENV"
   echo "CURL_EXIT=$CURL_EXIT" >> "$GITHUB_ENV"
   ```
2. **Robust Branching Condition:**
   ```bash
   elif [ "$STATUS" = "000" ] || [ "$CURL_EXIT" -ne 0 ] || { [ "$STATUS" -ge 500 ] 2>/dev/null; }; then

     echo "FAIL_MESSAGE=HTTP $STATUS (curl exit $CURL_EXIT): Server failure or timeout. The n8n server is down, unreachable, or returning internal 5xx errors." >> "$GITHUB_ENV"
   ```
